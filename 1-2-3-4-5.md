# Quality Review — Changes (1-2-3-4-5)

This document records the quality remediation performed on **Brarner.M.Alete**,
delivered in two pull requests:

- **PR A — Code quality (items 1–5):** `quality/dedup-signalprocessing-and-config-fixes`
- **PR B — Repository hygiene (items 6–10):** `hygiene/remove-binaries-and-artifacts`

---

## Part I — Code quality fixes (PR A)

### 1. Broken instance config paths

**Problem.** Every university `SignalProcessing.java` loaded a config path with a
dot instead of a slash:

```java
static { loadConfig("source-code/universities.appalachian/config.xml"); } // does not exist
```

The real file lives at `source-code/universities/appalachian/config.xml`. In total
**55 `loadConfig` paths pointed at files that did not exist.** The program did not
crash only because `loadConfig` swallowed the exception and silently fell back to
hardcoded defaults — so the instance configuration was never actually read.

**Fix.**
- The new shared engine resolves nothing by guesswork and **fails loudly**
  (`FileNotFoundException`) when a config is missing, instead of degrading silently.
- `BaseServer` computes each instance's config path from the module config's own
  directory + the instance name, so the dotted-path class of bug cannot recur.

---

### 2. Port collisions (all universities on port 9000)

**Problem.** The silent fallback in item 1 hardcoded `socketPort = 9000`, and on top
of that **51 of 53 university `config.xml` files literally contained**
`<socket-port>9000</socket-port>` — a stale copy-paste default that contradicted the
authoritative per-instance port declared in `source-code/universities/config.xml`
(e.g. `appalachian` is `port="8000"` there). Only one instance could ever bind; the
rest would die with "Address already in use."

**Fix.**
- Realigned all 51 stale university instance configs so each `<socket-port>` matches
  its authoritative module-config port within the `8000–8052` range.
- `BaseServer` now **skips any duplicate or out-of-range port** with a logged warning
  rather than letting instances collide.
- Hardened module-config parsing so the alternate `chemistry-config` schema (which has
  no `port-start`/`port-end`) no longer throws a `NullPointerException`.

---

### 3. Empty entry point

**Problem.** `Main.java` was documented as the "Application entry point" but was an
empty class (`public class Main {}`) with no `main` method.

**Fix.** `Main.java` is now a real entry point that delegates to `BaseServer`.

---

### 4. Massive copy-paste duplication (~8,960 files)

**Problem.** `SignalProcessing.java` was copy-pasted **~8,960 times** — once per
instance — and the copies were byte-for-byte identical except for *data* (package
name, config path, port, and output label strings). They totaled ~43 MB of source,
and **none of them were referenced by any code** (`BaseServer` only read config and
echoed received sample counts). Any single bug fix had to be applied thousands of
times.

**Fix.**
- Introduced **one** shared, parameterised engine:
  `source-code/bma/SignalProcessing.java` (package `bma`), driven by each instance's
  identity + its `config.xml`.
- Deleted all 8,960 per-instance copies. Instance directories now contain only their
  `config.xml` (which already held the real per-instance metadata).

---

### 5. Documentation out of sync with reality

**Problem.** `README.md` / `STRUCTURE.txt` claimed the species module held
"**35 phyla, 11 active**" and the project had "**Total: 1,645 instances**." In fact
`source-code/species/` is a nested taxonomic tree (phylum → class → family, up to 4
levels deep) of **7,348 instances**, and the real project total is **8,959**.

**Fix.** Updated `README.md` and `STRUCTURE.txt` to reflect:
- the real species taxonomy (35 phyla → 7,348 nested instances),
- the corrected totals (8,959),
- the shared signal-processing engine (no more per-instance copies),
- `Main` as the entry point.

### Verification (PR A)

- Core classes compile cleanly under `javac 25`.
- Running `BaseServer` against the real config starts **117 active instances across
  all modules on unique ports with zero collisions and no exceptions** — universities
  bind `8000–8052` instead of all fighting over `9000`, and all 5 chemistry instances
  come up (the previous NPE is gone).

## Part II — Repository hygiene (PR B)

Before: **~424 MB** of tracked binaries across **162** `.jar/.dll/.so/.zip/.class`
files. After: **~202 MB** — a **~222 MB** reduction. `2,201` files removed from
tracking; `.gitignore` corrected so none of them can silently return.

### 6. Build output committed to git

**Problem.** `out/artifacts/Brarner_M_Alete/Brarner.M.Alete.jar` (9 MB) — a build
artifact — was checked in, even though `build.sh` writes build output to the
`.gitignore`d `build/` directory.

**Fix.** Removed `out/` from tracking and added `out/` (and `build/classes/`) to
`.gitignore`.

### 7. JVM crash dump committed

**Problem.** `hs_err_pid38900.log` — a 6,382-line JVM `SIGSEGV` crash dump — sat in
the repository root.

**Fix.** Deleted it and added `hs_err_pid*.log` / `replay_pid*.log` to `.gitignore`.

### 8. IDE files tracked

**Problem.** `.idea/` IDE configuration (8 files) was tracked, and the `.gitignore`
only excluded a handful of specific `.idea` files rather than the directory.

**Fix.** Untracked `.idea/` and changed the ignore rule to `.idea/`.

### 9. Duplicate / stale binaries

**Problem.**
- The entire JavaFX 26 SDK was present **twice**: the standalone
  `jars/java-fx/javafx-sdk-26.0.1/` **and** a nested copy inside
  `jars/java-fx/openjfx-26.0.1_linux-x64_bin-sdk/javafx-sdk-26.0.1/` (23 MB, identical
  `lib/`), plus a 51 MB `javafx-jdk.zip` of it.
- `jars/java-fx/openjfx-26.0.1-javadoc/` — 88 MB / 2,108 files of vendored HTML API
  docs, not referenced by the build and freely available at <https://openjfx.io>.
- jDSP was duplicated: both `jdsp-3.1.0.jar` and `jdsp-3.1.1.jar` on the classpath
  (`build.sh` globs **all** jars, so two versions is a real class-resolution hazard),
  plus `jdsp-3.1.0.zip` **and** `jdsp-3.1.0 (1).zip` (22 MB each). `pom.xml` declares
  jDSP **3.1.1**.

**Fix.** Removed the nested `openjfx-..._bin-sdk/`, the `javafx-jdk.zip`, the
`openjfx-26.0.1-javadoc/` docs, the stale `jdsp-3.1.0.jar`, and both
`jdsp-3.1.0*.zip` files. Kept the standalone `javafx-sdk-26.0.1/` and `jdsp-3.1.1.jar`
(the versions the build actually uses). The classpath now resolves a single jDSP.

### 10. `.gitignore` entries that did not match

**Problem.** A "Large files (>50MB)" section in `.gitignore` listed
`jars/java-fx/javafx-sdk-26.0.1/bin/jfxwebkit.dll` (92 MB) and
`jars/java-fx/javafx-jdk.zip` (51 MB) — yet **both were committed anyway**, because the
entries had not actually kept them out.

**Fix.** Removed both files from tracking (so the entries now correspond to reality)
and extended the section to also cover the nested SDK, the javadoc dir, and the stale
jDSP artifacts, with comments explaining each.

### Verification (PR B)

- `git check-ignore` confirms every removed path (`out/`, `hs_err_pid*.log`, `.idea/`,
  the JavaFX zip/javadoc/nested-SDK, and `jdsp-3.1.0.jar`) is now ignored.
- The signal-processing classpath contains a single jDSP jar (`3.1.1`), matching
  `pom.xml`.
- The standalone `jars/java-fx/javafx-sdk-26.0.1/` SDK that the build uses remains
  intact.

## Not included (future work)

The following review findings were **not** addressed in these two PRs and remain open:

- **Two disconnected build systems.** `build.sh`/`build.bat` compile `source-code/**`
  into `Brarner.M.Alete.jar`, while `pom.xml` is a separate multi-module Maven project
  (`projects`, `primary-source`, `servlets`, `ejbs`, `ear`) that does not reference
  `source-code/` at all. `pom.xml` also targets **Java 9** while the repo bundles
  **JavaFX 26**.
- **Hardcoded DB credentials.** Thousands of instance configs hardcode
  `db-user=root` with an empty password to a local MySQL database.
- **No JDBC connection pooling / no driver registration** in the engine's
  `writeToDatabase` path.
- **Remaining large vendored binaries** (`onnxruntime` 90 MB, `pytorch-native` 73 MB,
  and the rest of the JavaFX SDK) would be better managed via a dependency manager
  (Maven/Gradle) or Git LFS rather than committed to git history. Note: removing files
  from tracking (as done here) stops them growing *future* history but does not shrink
  *existing* history; a history rewrite (e.g. `git filter-repo`) would be required to
  reclaim that space, and is intentionally out of scope.
